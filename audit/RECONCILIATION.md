## 1. Findings the sweep proved

### 1.1 `openjev` is not a component — it is a rename

`registry/components.yaml` lists `openjev` as an independent decision component
with `repo: kvnloo/openjev`. Observation:

```text
kvnloo/openjev  ->  resolves to kvnloo/z0intelligence (non-fork, default master)
```

The repo was renamed. Keeping `openjev` as a peer component of `z0intelligence`
is a **duplicate ownership claim over one repository**. Per z0#1 this becomes
`legacy_of: z0intelligence` with alias provenance only.

### 1.2 `memento` is a 2024 fork, not the memory authority

`registry/components.yaml` lists `memento` (`kind: memory`, `status: idea`,
`repo: kvnloo/memento`). Observation: it is a **fork**, upstream last active
`2024-04-23`, and it is a screen recorder.

A 2024 screenshot recorder cannot be the current runtime memory component.
It is reclassified `legacy_or_donor`, retained only as a prospective-sensor
candidate. **Zer0 has no memory authority today** — see §4.

### 1.3 `blueprint`'s description is stale, and its referent is a product line

z0#1 flagged `blueprint` as "possibly belonging" and the earlier review guessed
it was a vertical-farming digital twin. Both are half right. Observation:

- the GitHub **description** says: *"Product blueprint monorepo: architecture, brand, specs"*
- its **open PRs** say: *PR #16 "Lead the pretotype with ATLAS / soil-to-cell"*,
  and `solarpunk` (the sibling repo) carries `feat(growtwin): Phase 0 staging`,
  `three-tier walk-in plaza`, `release: converge dev into main` across **442 open PRs**

So the vertical-farming/ATLAS reading is correct and the **description is
misleading**. But this is a **product line, not network architecture**: it must
not enter the almanac as core architecture. Classified `reference_only` /
product surface, and the stale description is itself a finding for §5.

### 1.4 `solarpunk` is not a legacy donor

Earlier review proposed `legacy/donor`. Observation: `solarpunk` is a live
non-fork repo with **442 open PRs**, active `2026-09-14`, carrying the
GrowTwin/ATLAS agritech line. It is legacy **relative to Zer0 architecture**,
but it is an actively developed product repo. Those are different claims and the
registry must not conflate them.

### 1.5 RLM has no repo of its own, and six parallel lineages

RLM is recorded as an OMP feature. Observation of the OMP fork
(`kvnloo/oh-my-pi`, itself a **fork**):


So the lineage is **not** unpushed — `exp/rlm-evidence-addressing` exists on the
remote — but it shares a single fork with 102 local branches across six
checkouts, and no branch has been designated canonical. Any document that
describes "the RLM design" as settled is describing one of six local worktrees.
RLM must be represented as its own context/evidence plane, with **one lineage
designated canonical before anything is claimed about it**.

### 1.6 `hermes-jev-skills` is a fork

Observed `fork=true` with branches `hermes-jev/omp-adapter`,

### 1.7 DeepSeek Harness is absent and OMP is mandatory — both wrong

`registry/components.yaml` declares `oh-my-pi` as `required: true` and the
`minimal` profile is `[oh-my-pi]`. Meanwhile `deepseek-harness` appears **nowhere**
in the registry, despite being a primary execution surface (it is a fork of
`deepseek-ai/deepseek-harness`, default `master`, pushed `2026-09-21`).

`required: true` on a *fork* encodes "install our fork of OMP" as the definition
of a minimal Zer0. That is the single largest architectural error in the registry.

### 1.8 Every dependency metadata claim is a pinned SHA with no authority record

`registry/components.yaml` pins OMP to `ref: d707478…` on branch
`rfc/interactive-performance-stack`. Observation: that branch is the head of
**open PR #77** (`rfc/interactive-performance-stack -> main`). So the registry's
"current architecture truth" for the runtime is *an unmerged PR on a fork*.
This is precisely the `tested_ref` vs `architecture_status` conflation z0#1 warns
about, and it is not a one-off: 19 external entities have live upstream heads
that no pinned SHA can represent.

### 1.9 The registry has no delegated-source records at all

z0#1 requires vLLM, Ollama, Hugging Face, LiteLLM, OpenRouter and OpenTelemetry
to have authority/discovery records. The sweep now carries all six as
`catalog_source` entities with `authority`, `discovers` and `cache_policy`, and
none of them is a repo — which is exactly why they must not be modelled as
components.

### 1.10 Stranded work is normal, and that is the point

Zero-drift does not mean zero risk. Across the owned repos the sweep observed
substantial unmerged work, e.g.:

Any architecture document written from a default branch alone is therefore
incomplete by construction. The ledger makes the gap visible per entity instead
of hiding it in a README.

## 2. Ownership resolution: "promotion" is overloaded across three systems

Three sources currently claim parts of the same word:

| Source | Claim |
|---|---|
| z0 PR #4 | Evolution Lab owns promotion gates |
| z0evals | z0intelligence owns promotion / shadow / canary |
| Evolution Lab | owns experiments and qualification evidence |

These are not actually in conflict — they describe **three different acts** that
share one word. The split below is consistent with what the ledger observed and
is proposed as canonical:

```text
Evolution Lab   decides whether a candidate CLEARS frozen experimental gates
                and emits qualification evidence (an experiment result)
                        │
                        ▼
z0evals         FREEZES and PUBLISHES the reproducible study that the evidence
                belongs to (immutable, citable, re-runnable)
                        │
                        ▼
z0intelligence  owns ACTIVATION: whether an eligible, qualified policy is
                actually put into shadow → canary → active routing
```

Stated as responsibilities:

- Evolution Lab **may not** activate anything, and **may not** edit z0evals studies.
- z0evals **may not** train or activate; it only freezes and publishes.
- z0intelligence **may not** declare a candidate qualified; it consumes
  qualification evidence, and it owns the activation state.

The word "promotion" should be dropped from the registry in favour of the three
unambiguous verbs **qualify** (Evolution Lab), **publish** (z0evals),
**activate** (z0intelligence).

> Status: **proposed, not yet canonical.** Verified against code only to the
> extent that the three repos exist with these boundaries; the activation state
> machine in z0intelligence and the publication schema in z0evals still need a
> joint review before this wording is frozen into the registry.

## 4. What must NOT be promoted to truth yet

The caution is **not to confuse freshness with certainty**.

1. **Q-Route.** `experiment/q-route-v0` is `local=True, remote=False`. Phase 1B
   exists with real results but the teacher table is still sparse, and the
   decision to densify before training was correct. It enters the almanac as
   `experimental / local_only`, linked to evidence, **never** as a fixed
   `Hammer → Qwen4B → Qwen9B` ladder. Encode the *router/gate semantics* and let
   measured evidence decide which arms occupy them.
2. **Sol-Pi.** There is no canonical `sol-pi` component. The verified position is
   a **mechanism family** — Action Fusion, ObservationPack, verified reduction,
   context economics — implemented in `sol-pi-omp` and `sol-pi-hermes`, with the
   measurement gap (causal/context lineage) still open in Tokenomics.
3. **Memory.** No current authority exists. `memento` is a 2024 fork; Hermes
   private state, Laya and any TencentDB work are unverified as memory
   architecture. This needs a dedicated audit, not a convergence claim.
4. **DeepSeek Harness.** Real and current, but it must enter through the harness
   abstraction — not as another hard-coded executor in z0.
5. **RLM.** Do not publish a single "RLM design" until one lineage is designated
   canonical; today the lineage is 6 local checkouts against 2 remote branches.

## 5. Corrections to apply to `registry/`

Ordered so that each step is verifiable:

1. Split `components.yaml` into **owned** vs **upstream** vs **delegated source**.
2. Remove `required: true` from `oh-my-pi`; replace with a harness capability
   requirement ("one supported harness"), and add `deepseek-harness` and
   `hermes-agent` as peer executor implementations **sourced from AODL's harness
   catalog**, not recopied.
3. Demote `openjev` to `legacy_of: z0intelligence`; keep the alias only.
4. Reclassify `memento` out of `kind: memory`.
5. Rewrite `kerdoios` to resource placement / quota / Pareto allocation.
6. Rewrite `z0intelligence` to the cognition plane (cf. the merged
   `feat/local-cognition-registry` work: `registry/cognition.yaml`).
7. Add owned: `z0evals`, `z0archy`, `dash`, `ripple`, `verified-oss-loop`,
   `hermes-keel`, `hermes-mesh-keel` (pre-activation), `hermes-jev-skills`,
   `sol-pi-omp`, `sol-pi-hermes`.
8. Add delegated sources: HF, vLLM, Ollama, LiteLLM, OpenRouter, OTel.
9. Replace `integrates_with` with typed edges (`executes_via`,
   `consumes_contract`, `emits_contract`, `discovers_from`, `measured_by`,
   `evaluated_by`, `publishes_evidence_to`, `legacy_of`, `reference_to`).
10. Separate `tested_ref` from `architecture_status`; stop presenting an
    unmerged PR SHA (`oh-my-pi` `rfc/interactive-performance-stack`) as truth.
11. Redesign profiles around capabilities + selected harness, not OMP inheritance.
12. Fix the stale GitHub descriptions found here (`blueprint` at minimum) — but
    that is a repo-metadata change, not a registry change, and should be tracked
    separately.

observation, and `unknown` is treated as "not yet asserted" rather than as a pass.

be applied to `registry/` by hand — the point of this branch is that the registry
is regenerated from reconciled truth, so that the next time RLM, Q-Route, DSH or
